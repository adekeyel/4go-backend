# forego backend — Railway/Postgres/Prisma edition

This replaces the Supabase backend (Postgres + Auth + Storage + Edge Functions +
Realtime + RLS) with a self-hosted Node/Express + Prisma + Socket.io backend,
deployable to Railway against your own Postgres instance.

## How this was built

The Prisma schema (`prisma/schema.prisma`) was **not** hand-typed or guessed
from the frontend. It was generated by:
1. Installing Postgres locally and running all 87 of your original Supabase
   migrations against a real database (with Supabase-only pieces like
   `auth.uid()`/RLS stubbed out, since those don't carry over).
2. Taking an authoritative `pg_dump --schema-only` of the result.
3. Parsing that real DDL into a Prisma schema.

This means every table, column, type, default, primary key, unique
constraint, and index in `schema.prisma` matches your actual production
schema — 56 tables total. Two models were added on top that didn't exist in
Supabase's `public` schema (because Supabase managed them internally):
`User` and `RefreshSession`, which now do the job Supabase Auth used to do.

**I could not run `prisma generate`, `prisma validate`, or `prisma migrate`
in the sandbox this was built in** — Prisma's engine binaries are fetched
from `binaries.prisma.sh`, which wasn't reachable from that environment. Run
these as your very first step on a machine with normal internet access:

```bash
npm install
npx prisma format      # auto-fixes minor formatting, will error loudly on anything invalid
npx prisma validate
npx prisma migrate dev --name init   # creates your first migration against DATABASE_URL
```

I'd expect this to work cleanly or need only minor touch-ups, since the
schema came from your real DDL — but I want to be upfront that this exact
step hasn't been run yet.

### Steps

```bash
npm install
npx prisma generate
npx prisma migrate dev --name init   # creates the schema on your new DB
npm run import:data                  # reads DATABASE_URL from your .env file
```

### About login credentials — read this

Supabase's dashboard CSV export only covers the `public` schema. Emails and
password hashes live in `auth.users`, which isn't included in a Table Editor
export, so **the accounts created by this import cannot log in yet** — each
user row is created with a real, correct `id` (matching every reference to
them across all your data) but a cryptographically random, unusable password
hash and no email.

To finish the job:
1. Run `scripts/export-auth-users.sql` in Supabase's SQL Editor (Dashboard →
   SQL Editor). It only reads `auth.users` — it changes nothing.
2. Download the result as CSV, save it as `scripts/data/auth_users.csv`.
3. Re-run `npm run import:data`. It will detect the file and patch in real
   emails + password hashes for the matching users, leaving everything else
   untouched.

Because Supabase's GoTrue and this backend's `bcryptjs` both use standard
bcrypt, existing users should be able to log in with their current password
immediately after this patch step — no forced reset. Worth verifying with
one real test login before telling users the migration is complete.

## Setup

```bash
cp .env.example .env   # fill in DATABASE_URL, JWT secrets, Cloudinary, Resend, Flutterwave
npm install
npx prisma generate
npx prisma migrate dev --name init
npm run dev
```

Deploying to Railway: add a Postgres plugin, set the env vars from
`.env.example` in the service settings, set the build command to
`npm install && npx prisma generate && npm run build` and the start command
to `npx prisma migrate deploy && npm start`.

## Architecture

- **Auth**: custom JWT (access + refresh). Refresh tokens are httpOnly
  cookies tied to a `RefreshSession` row per device, so logout/"log out
  everywhere" and token theft detection (rotation) both just touch that
  table. See `src/routes/auth.ts`.
- **Authorization**: Supabase's RLS policies are gone; the equivalent checks
  now live in route handlers/middleware (`requireAuth`, `requireSuperAdmin`,
  `assertRoomMember`/`assertRoomAdmin` in `routes/rooms.ts`). Any table you
  add routes for needs its own explicit checks — there's no longer a
  database-level safety net.
- **Realtime**: Socket.io (`src/sockets/index.ts`), replacing Supabase's
  `postgres_changes` subscriptions and broadcast channels. Rooms are joined
  as `room:${roomId}` / `user:${userId}`; route handlers call
  `emitToRoom`/`emitToUser` after writes (see `routes/messages.ts`).
- **Storage**: Cloudinary (`src/lib/cloudinary.ts`, `routes/uploads.ts`)
  replaces Supabase Storage buckets.
- **Email**: Resend, direct send (`src/lib/email.ts`) — simpler than the
  original Lovable webhook + queue architecture, since there's no longer a
  third-party platform in front of Supabase Auth to proxy through.
- **Payments**: Flutterwave, ported from `create-payment`/`verify-payment`
  edge functions (`src/routes/payments.ts`).

## What's fully implemented and verified against your real stored procedures

For these, I didn't just approximate — I read the actual `CREATE FUNCTION`
body in the pg_dump and ported the logic (rank gates, idempotency keys,
exact coin amounts, cooldowns) line-for-line:

| Feature | Route | Ported from |
|---|---|---|
| Signup/login/refresh/logout/password reset | `routes/auth.ts` | Supabase Auth (redesigned, not a port) |
| Profile get/update/search | `routes/profiles.ts` | RLS policies on `profiles` |
| Friends: request/accept/decline/list/block | `routes/friends.ts` | RLS policies on `friends`/`user_blocks` |
| Rooms: create/join/list/members, private-room join requests | `routes/rooms.ts` | `approve_join_request`, `reject_join_request` |
| Messages: send/edit/delete/reactions, realtime broadcast | `routes/messages.ts` | RLS + Realtime on `messages`/`message_reactions` |
| Feed: posts/likes/comments | `routes/feed.ts` | `toggle_post_like`, `add_post_comment` (simplified — no page-post variant yet) |
| File uploads | `routes/uploads.ts` | Supabase Storage |
| Wallet balance/transactions/withdrawals | `routes/wallet.ts` | **`request_withdrawal`** — exact rank tiers (Master/King), premium multipliers, monthly cap, 2-coins-per-₦1 rate |
| Daily coin claim | `routes/wallet.ts` | **`claim_daily_reward`** — 100 coins, 6h cooldown, max 3/UTC day |
| Coin purchases, premium subscriptions, verification applications | `routes/payments.ts` | **`buy_coins`**, **`activate_premium`**, **`submit_verification_application`** — idempotency keys, exact pricing (₦2,500/₦24,000 premium, ₦10,000 verification), rank gates |
| Admin: suspend/unsuspend/delete users, moderation reports, withdrawal approval | `routes/admin.ts` | `admin_suspend_user`, `admin_unsuspend_user`, `admin_complete_withdrawal`/`admin_reject_withdrawal` |

## What is NOT yet ported (still lives only in the old Supabase schema/edge functions)

This is a big app — 109 Postgres functions and 10 edge functions in total.
The list above covers the core account/chat/monetization loop. Not yet built:

- **Pages** (business/creator pages): `create_page`, `follow_page`,
  `unfollow_page`, `get_page_feed`, `boost_page_post`, `toggle_page_post_like`,
  `add_page_post_comment`, `record_page_post_view`
- **Contests**: `capture_contest_join_minutes`, `get_contest_leaderboard`,
  `reward_contest_participant`
- **Status/Stories**: viewing, reactions (`statuses`, `status_views`,
  `status_reactions` tables exist in the schema; no routes yet)
- **DMs as a special room type**: `get_or_create_dm_room`
- **Mentions**: `record_mentions`, `search_mentionable_users`
- **Gifting**: `send_gift`, `send_gift_to_post`
- **Referrals**: `process_referral`, `generate_referral_code`,
  `employee_downline`, `employee_invited_users`, `employee_pipeline_stats`
  (the whole referral/employee-dashboard feature)
- **Push notifications**: `notify_push_on_message`, `notify_push_on_mention`,
  web push subscription handling (`push_subscriptions` table exists; no
  VAPID send logic wired up yet, though `.env.example` has the keys ready)
- **Support tickets**: `support_conversations`/`support_messages` tables,
  `set_support_status`, `can_support`
- **Admin analytics dashboard**: `admin_platform_stats`,
  `admin_daily_metrics`, `admin_message_type_breakdown`,
  `admin_security_overview`, `admin_flagged_accounts`, and ~15 other
  `admin_*` reporting functions
- **Presence/online-minutes tracking**: `increment_online_minutes`,
  `calculate_rank` (the rank-threshold logic itself — `Amateur` through
  `King` — needs porting; right now rank only changes if you write to it
  directly)
- **Email queue/DLQ system**: the original had a durable pgmq-based queue
  with retry/backoff; this rewrite sends email directly and synchronously
  instead, which is simpler but less resilient to transient Resend outages

None of these have database tables missing — the Prisma schema already has
every table for all of the above. It's purely the route/business-logic layer
that's outstanding.

## What is NOT done at all (separate, large piece of work)

**The frontend still calls `@supabase/supabase-js` everywhere** — none of
the ~150+ `supabase.from(...)`/`supabase.rpc(...)`/`supabase.auth.*` call
sites in the React app have been touched. That swap (to a fetch-based API
client hitting this new backend, plus a Socket.io client replacing the
Realtime subscriptions) is its own substantial task and hasn't been started.
